# visual-benchmarking
- When the user sends a screenshot of another person's/competitor's portfolio or project with a request to "impress me", treat the screenshot as a visual specification to match or exceed — analyze the visual quality, layout, polish, and details in the reference image, then upgrade the user's own project to at least that level of polish while preserving their unique theme/aesthetic (colors, branding, dark/cyber style). Apply premium upgrades like animated gradient rings, glow effects, hover animations, enhanced shadows, and larger/more polished card layouts. Do not ask clarifying questions — execute the upgrade directly from the screenshot reference. Confidence: 0.70
- The user's quality benchmark for premium design is SaaS brands like **Vercel, Linear, OpenAI, Framer, and Raycast** — "Minimal, modern, compact, responsive, and premium." When told to make something look premium, aim for that level of polish: clean hierarchy, tight spacing, compact cards, subtle gradients/glows, refined micro-interactions, and restraint over decoration. The aesthetic should be award-worthy portfolio quality, not generic. Confidence: 0.85

# animation
- Add heavy, impressive animations on every page, every interaction, and during loading states — animations should be visible everywhere to impress. Prefer **fast, energetic animation speeds** (not slow/ambient) to create a dynamic, modern tech feel; when increasing animation speed, always pair with performance optimizations (GPU-composited properties like transform/scale/opacity, `will-change`, hardware acceleration) to prevent frame drops at higher velocities. Use Framer Motion with a custom `easeOut` cubic-bezier easing (`[0.25, 0.46, 0.45, 0.94]`), durations of 0.4s–0.8s, and **no excessive bouncing** or spring overshoot for a polished, professional feel. Use `useInView` for scroll-triggered reveals (fade up, slide, scale, stagger reveal) with `once: true` so animations play only on first scroll entry. The user will explicitly reject animation work that does not meet a premium/impressive standard — subtle or basic animations will receive negative feedback ("not impressed"). Confidence: 0.95
- **Performance > visual effects** — Never sacrifice performance for visual effects. If there's a trade-off between flash and speed, always choose performance. Every animation must use ONLY GPU-composited CSS properties: `transform` and `opacity`. Avoid expensive CSS properties (layout-triggering properties like `width`, `height`, `top`, `left`, `margin`, `padding`, `background-position` being animated on main thread). Maintain a consistent 60 FPS. Use `will-change: transform` on animated elements, `memo`/`useMemo` for stable component trees, and `requestAnimationFrame` for custom animation loops. The user will reject any animation work that causes jank, stutter, or frame drops — polish is meaningless if it degrades performance. Confidence: 0.90
- **Purposeful over flashy animations** — Every animation must have a purpose (guiding attention, communicating state transition, providing feedback). Never add animations purely for decoration or "because they look cool." This applies to all animation categories: entrance reveals, hover effects, loading sequences, and micro-interactions. A purposeful animation is one that improves UX clarity or brand perception; a flashy one that doesn't serve those goals will be rejected. Confidence: 0.85
- **Distinguish interaction animations from ambient background motion** — User-facing interaction animations (hover states, button clicks, section entrances, loading sequences) should use the fast/energetic speeds (0.3s–0.8s, cubic-bezier easing) specified elsewhere. Separately, **background ornamental elements** (grid patterns, neural network lines, floating particles, gradient orbs/blobs) should use **very slow, almost-unnoticeable drifting motion** (20s+ cycle durations, ±few pixels, no chaos, no rapid movement). Background particles should look like "AI energy" — not like snow, not like stars. The grid should shift so slowly it feels alive but never draws attention. Neural network nodes/connections should drift smoothly with no stuttering. All background ambient motion must use `pointer-events: none` and `will-change: transform`. Confidence: 0.85
- **"Live AI System" feel** — The portfolio should feel like a live operating system, not just a collection of animations. This means: (a) a terminal/status badge showing system state (e.g., "AI Systems: Online | Engine: Active"), (b) a metrics strip with live-animated counters (e.g., "Projects Deployed, AI Models Built, Client Satisfaction %"), (c) floating neural network nodes with connecting lines that pulse and drift, and (d) section transitions that make the entire site feel like a cohesive AI operating system rather than a traditional portfolio. This goes beyond decorative animations into a coherent narrative of the site being a "living system." Confidence: 0.85

# backend
- All API routes should have robust try/catch error handling with proper HTTP status codes (400/500) and meaningful error messages returned in the response — never silently swallow errors or return null. Confidence: 0.80
- When querying Supabase for a single row with `.maybeSingle()`, always chain `.limit(1)` before it (e.g., `.limit(1).maybeSingle()`) to prevent the "JSON object requested, multiple rows returned" error when duplicate rows exist from migration re-runs or seed scripts. This applies everywhere, including admin CRUD routes and public data fetches. Confidence: 0.85
- When writing Supabase admin update/upsert routes, prefer a two-step pattern over `.upsert()`: first fetch the actual existing row's real ID using `.limit(1).maybeSingle()`, then apply `.update(req.body).eq('id', existing.id)`. This avoids problems when (a) the table has duplicate rows from migration re-runs, (b) the frontend sends a hardcoded/fixed UUID that doesn't match the auto-generated UUID in the database, or (c) `.upsert().select()` throws because of multiple matching rows. Only fall back to `.insert()` when no existing row is found. Confidence: 0.85
- In the client-side catch blocks, always convert error values to strings before storing in React state (e.g., `setError(typeof raw === 'string' ? raw : String(raw))`). React throws error #31 when trying to render an object (`{code, message}`) as a JSX child, so defensive string coercion prevents this crash. Also provide specific user-facing messages for common HTTP errors (500 → "Server error. Check env vars on Vercel.", ERR_NETWORK → "Cannot reach server.") rather than blindly displaying the raw error. Confidence: 0.85
- API keys for external services (AI providers, etc.) should be configurable via a frontend admin UI dashboard, support multiple providers simultaneously, and allow seamless key rotation without system disruption when keys expire or hit rate limits. Confidence: 0.80

# deployment
- When deploying a Vite + Express app to Vercel (or similar serverless platforms), server runtime env vars must NOT use the `VITE_` prefix — that prefix is exclusively for Vite build-time client injection. The server config should check both the non-prefixed name (for Vercel/production) and the `VITE_` prefixed name (for local dev compatibility) as fallbacks, so the same code works in both environments without duplicate env var setup. Confidence: 0.85
- On Vercel (or any serverless platform), wrap `dotenv.config()` in try/catch — the `.env` file is typically gitignored and won't exist in the deployed environment. An unguarded `dotenv.config()` that tries to load a non-existent file can crash the serverless function on cold start. Add startup logging (`console.log`) to print which env vars are present before serving requests, so missing vars are visible in the platform's function logs. Confidence: 0.85

- When VITE_ prefixed env vars (e.g., `VITE_SUPABASE_URL`) are needed by both the Vite build and the Express server at runtime, use a **build-time env var injection pipeline**: create a `scripts/generate-env.js` script that snapshots the build-available `VITE_` vars into a file deployed alongside the serverless function (e.g., `api/server.env`); run this script as the last step of `vercel.json`'s `buildCommand` (`cd client && npm run build && cd .. && node scripts/generate-env.js`); and have the server config load it via a secondary `dotenv.config()` fallback. This bridges the gap because Vercel injects `VITE_` vars only during the build step, not at serverless runtime. Add the generated file to `.gitignore`. Confidence: 0.85
- On Vercel (serverless), use a **single** serverless entry point — NOT two competing files. Having both `api/index.js` (handles exactly `/api`) and `api/[...slug].js` (catch-all) creates separate Lambda functions that can unpredictably split traffic. Remove `api/index.js` and route ALL `/api/*` traffic through the catch-all only. Add an explicit `/api/(.*)` rewrite in `vercel.json` pointing to the catch-all destination to ensure no routing ambiguity. The `functions` config in `vercel.json` must target the catch-all file, not `api/index.js`. Confidence: 0.85

# accessibility
- Pages must follow proper heading hierarchy (h1 → h2 → h3), include ARIA labels on interactive elements, support keyboard navigation, maintain sufficient color contrast for readability, and use semantic HTML elements. Also respect `prefers-reduced-motion` so users with motion sensitivity are not overwhelmed by animations — animations should degrade gracefully (fade transitions instead of slide/scale/stagger) rather than being disabled entirely. Confidence: 0.75

# secrets-management
- Never hardcode API keys, secrets, or credentials in source/config files that get committed to git — use environment variable placeholders (e.g., `${VARIABLE_NAME}`) in committed code and provide actual values via environment variables, runtime configuration, or admin UI settings. If secrets are accidentally committed, use `git filter-branch` (or `git filter-repo`) to purge them from all historical commits, then force push. Confidence: 0.90

# coding-style
- When building or redesigning pages, refactor them into small, focused reusable sub-components (e.g., dedicated files for hero, cards, timeline, stats, section titles) rather than one monolithic page component. Each sub-component should have a single responsibility. Avoid duplicate logic across these components. Confidence: 0.75
- When redesigning or building UI sections, do NOT introduce unnecessary third-party libraries — keep existing React components and CSS patterns, reuse current styles where possible, remove duplicated CSS, and use clean semantic HTML. Prefer a lightweight, dependency-minimal approach even during significant layout overhauls. Confidence: 0.80
- When deleting/removing a feature or section of code, proactively audit the file for now-unused imports, destructured variables, and references — clean them up in the same pass rather than leaving dead imports that could trigger build warnings or confuse future developers. Confidence: 0.80
- File download links (resume/CV, PDFs, documents) must use the HTML `download` attribute on the `<a>` tag so clicking triggers a file download instead of navigating to or opening the file in a new tab. Never use `target="_blank"` for downloadable files — always use `download` (optionally paired with a polished UI). Confidence: 0.85
- **Never define React components (or sub-components like `Input`, `TextArea`, `Label`) inside the body of another component** — e.g., `const Input = (props) => <input ... />` inside a `function MyPage() { ... }`. Every render creates a new function reference, which React interprets as a different component type, causing it to unmount the existing DOM node and remount a new one. For controlled `<input>` elements, this destroys the cursor position. Instead, extract CSS class names to module-level `const` strings (e.g., `const inputClass = 'w-full px-4 ...'`) and use native HTML elements (`<input className={inputClass} />`) directly in the JSX. This ensures stable DOM identity across re-renders and preserves cursor position during text editing. Confidence: 0.95
